# ADR-002: リアルタイム同期プロトコル（コマンド / イベント / スナップショット）

- Status: Proposed
- Date: 2026-11-10
- 関連: [ADR-001](001-server-authoritative-visibility.md)

## 背景
旧 Fortuna は Photon 利用で同期処理が複雑化し、頓挫した。
FortunaVTT は ASP.NET Core + SignalR（WebSocket）を使い、サーバー権威で単純な同期モデルにする。
秘匿のため、受信者ごとに配信内容が異なる点が通常のブロードキャストと違う。

## 決定

### 1. 通信の基本形
クライアント→サーバーは **Command**、サーバー→クライアントは **Event** のみ。
クライアントは状態を直接書き換えず、Event を適用して状態を更新する。

```
Client --Command--> Hub --検証/適用--> Room(状態) --Event--> Visibility --> 各Client
```

### 2. ルームは単一ライター
1ルームの状態変更は、ルームごとの直列キュー（`Channel<T>` 等）で1本のループが処理する。
これにより、ルーム内の競合・レースコンディションを構造的に排除する。
ロックは使わず、キューに積む処理のみ並行とする。

### 3. 配信は「接続ごと」に絞り込む
SignalR のグループ一括配信は使わない（全員に同じものが届いてしまうため）。
Room が Event を生成 → Visibility 層が受信者ごとに「見せてよいか／見せる形」を決定 → 接続ごとに送信。

- 見えない Event は送らない。
- 一部だけ見える場合は、**受信者向けに加工した Event**（例: 秘密のダイス結果を伏せる）を送る。
- 見える範囲が変わった場合（公開など）は、その時点で追加の Event を送る。

### 4. 順序と再接続
- ルームごとに単調増加の `seq` を採番し、全 Event に付ける。
- 受信者ごとに欠番が生じうるため、`seq` は受信者単位で連続とは限らない。
  欠番検知は、サーバーが各クライアントに送る **最終 seq（heartbeat）** との照合で行う。
- 再接続時は、クライアントが `lastSeq` を送る。
  - 保持範囲内: サーバーが差分 Event を再送する（受信者ごとに再フィルタ）。
  - 範囲外: **受信者向けスナップショット**を送る。
- スナップショットも必ず Visibility 層を通す。

### 5. コマ移動などの高頻度操作
- ドラッグ中は `Preview`（揮発・保存しない・間引き可）を送る。
- 確定時のみ `Command` を送って永続化する。
- クライアントは楽観的に動かし、サーバーの Event で確定または巻き戻す。

### 6. メッセージ形式
- 当面は JSON（デバッグしやすさ優先）。
- 負荷が問題になった時点で MessagePack に切り替える。

### 7. Command の基本ルール
- すべての Command は `commandId`（クライアント生成の GUID）を持つ。冪等性と ACK/エラー対応に使う。
- サーバーは必ず Command を検証する（権限、対象の存在、可視性）。
- 見えない対象に対する操作は、「存在しない」と同じエラーを返す（存在の漏洩を防ぐ）。

## M1 で扱う Command / Event
| Command | Event |
|---|---|
| `JoinRoom` | `RoomJoined`（スナップショット含む） |
| `SendChat`（公開／秘話） | `ChatPosted` |
| `RollDice`（公開／秘密） | `DiceRolled` |
| `MoveToken` | `TokenMoved` |

## 未決事項
- 認証: ルームパスワードのみか、アカウントを持つか。
- 永続化: 現在状態のみ保存するか、Event ログを保存するか。
  M1 は「現在状態＋チャットログ」で十分と考えている。
- 水平スケール: 当面は単一サーバー前提（ルームは1プロセスに固定）。

## 結果
- 利点: 競合がなく、秘匿をサーバーで保証でき、再接続も整理できる。
- 欠点: 受信者ごとの配信でサーバー負荷が増える。単一プロセス前提では横展開が難しい。

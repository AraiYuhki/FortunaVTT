# ADR-003: アカウント認証と「ロビー・ルーム・ユーザー」構造、公開先の管理

- Status: Proposed
- Date: 2026-11-10
- 関連: [ADR-001](001-server-authoritative-visibility.md), [ADR-002](002-realtime-sync-protocol.md)

## 背景
- 秘匿の単位は「個人」である。どどんとふは個人ごとの可視状態をサーバー側キャッシュに持っていた。
- ゲストではなく**アカウント制**とし、将来 Google アカウント連携を可能にする。
- 個々人が、自分のデータや素材を「誰に公開するか」を決められる必要がある（ルーム内の操作）。

## 決定

### 1. 構造: ロビー / ルーム / ユーザー
| 単位 | 役割 |
|---|---|
| **User** | アカウント。ログイン主体。素材ライブラリ（個人所有）を持つ。 |
| **Lobby** | ルームの一覧・作成・参加の入口。ログイン後の最初の場所。リアルタイム同期の対象は最小限（ルーム一覧の更新程度）。 |
| **Room** | 1つの卓。状態・チャット・ダイス・コマ・マップはすべてルームに閉じる。ルームごとに単一ライターの直列キュー（ADR-002）。 |

- 1ユーザーは複数ルームに所属できる。
- **公開先の操作はルーム内限定**。ロビーには「公開」の概念を持ち込まない。
- ルーム内のロール: `Owner`（ルーム管理者）/ `Member` / `Observer`。ロール定義は Room に属する。
- **「GM」はシステム上のロールではない**。GM は卓ごと・場面ごとに変わるため、特権を持たせない。
  GM 役の人は、他のメンバーと同じく、自分が所有するものの公開先を指定して運用する。
- `Owner` は管理権限（メンバーの追放・ルーム削除・Owner 移譲）のみを持ち、**他人の非公開データを見る権限は持たない**。
- **例外はサーバー管理者のみ**（下記 §3）。サーバー管理者はルームのロールではなく、ユーザー（アカウント）の属性である。

### 2. 認証
- **ASP.NET Core Identity** + EF Core（SQLite 開始）でローカルアカウント（メール + パスワード）を実装する。
- **Google 連携は後付け**できるよう、外部ログインを `UserLogin`（provider, providerKey）として分離し、
  ユーザー本体（`UserId`: GUID）は認証手段に依存させない。
- HTTP は Cookie 認証。SignalR は同一オリジンの Cookie、または短命のアクセストークンで認証する。
- ゲスト参加は M1 では提供しない。
- ルームへの参加は、招待リンク（＋任意のルームパスワード）で行う。参加にはログインが必須。
- Hub 側はすべて `UserId` を信頼の起点にする。クライアントが名乗るユーザー ID は一切信用しない。

### 3. 公開先（Audience）モデル
- ルーム内の各「共有対象」（コマ、マップ、カード、チャット、素材参照など）は、**所有者（Owner）** と **公開先（Audience）** を持つ。
- 公開先の種類:
  - `OwnerOnly`（自分だけ）
  - `Members { userIds }`（指定したメンバーだけ）
  - `Room`（ルームの全員）
- 変更できるのは所有者のみ。
- **GM・ルームの Owner を含め、非公開データを閲覧できる特権者は存在しない**（決定）。
- **唯一の例外はサーバー管理者**（決定 2026-11-10）。
  - 全ルームのすべてのオブジェクトを**閲覧**できる。ルームに参加していなくても、退室していても見える。
  - 権限は**閲覧のみ**。他人のオブジェクトの編集・削除・公開先変更はできない。
  - サーバー管理者かどうかは、サーバー側のアカウント属性で決まる。クライアントの申告は信用しない。
  - 帰結: 所有者がいない間、`OwnerOnly` のデータは、所有者以外にはサーバー管理者だけに見える。
  - 監査ログ（誰がいつどのルームを閲覧したか）を残す方針。実装は後続（未決事項 2）。

### 4. 見えている集合のキャッシュ（差分配信の基礎）
- サーバーは接続（ユーザー）ごとに **ViewState**（今見えている対象 ID と版）を保持する。
- 状態変更・公開先変更のたびに、Visibility 層が前後の可視性を比較して、次を生成する。
  - 見えるようになった → `Appeared`（完全な内容を送る）
  - 見えなくなった → `Disappeared`（IDのみ）
  - 見えたまま変化 → 通常の差分 Event
- ViewState は再接続時にスナップショット生成にも使う（ADR-002 §4）。
- ViewState はメモリ上のキャッシュであり、**正は永続化された所有者・公開先データ**。落ちても再計算できる。

### 5. 素材（画像・音声など）
- 素材は**ルームに属する**。アップロードしたユーザーが所有者となり、Audience を指定する。
- 全ルーム共通の **テンプレート素材**（[ADR-004](004-template-assets.md)）は読み取り専用で、ルームには属さない。
- ユーザーの個人ライブラリ（ルーム横断で再利用）は将来の検討事項とし、M1 では持たない。
- **ファイル配信にも同じ可視性判定を適用する**。推測できない URL だけに頼らず、
  素材の取得は認証必須のエンドポイント経由とし、リクエストごとに「このユーザーに見せてよいか」を判定する。
  （画像URLが漏れると、Event を絞っても秘匿が破れるため）
- 公開されなくなった素材は、取得要求を「存在しない」として扱う。

### 6. 退室・追放・ルーム削除（決定）
| 事象 | 所有物（オブジェクト・素材）の扱い |
|---|---|
| **退室** | ルームに**残す**。Audience も維持。再参加すれば所有権を保ったまま復帰する。 |
| **追放** | そのユーザーの所有物を**すべて削除**する。 |
| **ルーム削除** | ルームに属する**素材・オブジェクトをすべて削除**する（ファイル実体も削除）。 |

- 削除は DB とファイル実体の両方を対象にし、途中失敗に備えて「削除予約 → 実削除」の二段階にする。
- 追放は、削除の確認を Owner に求める（取り消せないため）。

### 7. 最低限のデータモデル（概念）
```
User(Id, DisplayName, Email, ...)         UserLogin(UserId, Provider, ProviderKey)
Room(Id, Name, OwnerUserId, ...)          RoomMember(RoomId, UserId, Role, State: Active|Left)
Asset(Id, RoomId, OwnerUserId, Audience, ...)
RoomObject(Id, RoomId, OwnerUserId, Audience, ...)
```

## 未決事項
1. **メールの扱い**: アカウント復旧に必須か。Google 連携後はメールなしでも可とするか。
2. **サーバー管理者の運用**: 閲覧の監査ログ、ユーザーへの周知（利用規約など）、BAN・アカウント削除の範囲。
   閲覧はできても編集はできない点は決定済み。
3. **Owner の退室**: 暫定実装は「Owner は移譲しないと退室できない」。この方針でよいか確認する。
4. **所有者不在の `OwnerOnly` データ**: 長期間戻らない場合の扱い（保持期限など）。

## 決定済み（2026-11-10）
- GM の特権なし（案B）。GM は固定ロールではない。
- 退室は所有物を残す／追放は削除／ルーム削除は素材を全削除。

## 結果
- 利点: 秘匿の単位が個人に統一され、素材ファイルまで一貫して守れる。Google 連携を後付けしても、ドメインに影響しない。
- 欠点: 素材配信を毎回判定するため、単純な静的配信より実装・負荷が重い。ViewState の整合性管理が必要。
